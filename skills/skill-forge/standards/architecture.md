# 标准S2 — 分层架构（T0/T1/T2 分诊 + 各层规范）

> Mode A 的 A1 步、Mode B 的 B3 步必读。核心原则：**架构跟着复杂度走，反对一刀切**。

## T1 分诊表

| 判据（任一命中即升级） | T0 单文件 | T1 标准模块化 | T2 流水线级 |
|---|---|---|---|
| 规模 | ≲150 行、单一任务 | 数百行、多领域规则 | 多阶段流程 |
| 模式数 | 1 | 1–2 | ≥2 或链式模式 |
| 有无阶段中间产物 | 无 | 无硬需求 | 有（JSON/表格落盘传递） |
| 有无可确定性计算 | 无 | 少量 | 有（估时/校验/换算→脚本） |
| 规则间引用密度 | 低 | 中 | 高（需要编号体系） |
| 跨工具共享需求 | 弱 | 中 | 强 |

| 层级 | 应包含 | 不应包含 |
|---|---|---|
| **T0** | 单个 SKILL.md（frontmatter 合规 + 正文聚焦单一任务） | rules/、docs 套件、scripts |
| **T1** | SKILL.md 瘦总控 + knowledge/ 或 rules/ 若干领域文件 + 精简 checklist；可选 README | manifest、audit 双门、lint（除非规则编号已出现） |
| **T2** | 总控 + workflows/ + rules/(编号) + review/(preflight+audit) + scripts/ + reference/ + 文档三件套 + lint_skill.mjs + pipeline\manifest.json 产物约定 | —— |

行数只是提示，判据优先。拿不准就选低一档，后续可升级（CHANGELOG 记录升层事件）。

## T2 总控规范（T1 参照执行）

- 目标 ≤200 行。只允许六块：铁律(≤7条) / 模式触发表 / 产物与状态约定 / 阶段调度表 / 断点续跑与回退 / File Map+维护约定。
- 阶段表每行必须五列齐全：Stage | 做什么 | **必读文件**(精确路径) | 输出 | 通过条件+失败回退。"凭记忆执行"不允许存在。
- 禁止出现任何规则正文、示例、速查表——它们属于 rules/ 或 reference/。
- 维护约定必须指向 MAINTENANCE.md 并要求改后跑 lint。

## T3 规则模块规范

- 一个领域一个文件；文件头注明作用域与编号前缀。
- 编号 `[A-Z]{2,6}-\d{2}`，全技能唯一，**只增不复用**（废止也要留档"由谁取代"）。
- 单一事实源：规则正文只在此定义；workflows/review/SKILL.md 只写"动作 + 编号引用"。
- 新规则必须同步登记到审查清单（preflight/audit 对应分组加一行引用），否则视为死规则（lint C2 会提示）。

## T4 审查双门规范（T2）

- **Preflight（内容门）**：逐项清单，每项括号标注规则出处编号；开头写明三条使用原则（要素计数、证据绑定、禁字数下限——见 anti-lazy.md）。
- **Audit（执行门）**：A1…An 表格，含"证据要求"列；两段式时机（中途门+终审）；报告随交付强制输出，缺失=任务未完成；补执行与再触发条款必备。

## T5 产物与状态（流水线类）

- 中间产物落盘 `{工作目录}\pipeline\`，JSON/Markdown 表格，命名带序号（01_…02_…）。
- manifest.json 记录各 stage status，断点续跑依据；任一审查 ❌ → 受影响 stage 及其后置回 pending 重跑。
- 可确定性计算一律脚本化（node/pwsh），AI 只做创意复核；脚本头注释写用法+映射的规则编号。

## T6 过度工程警报

出现以下情形立即降档：模块文件 <40 行且仅一个使用者；checklist 引用的规则不存在；为"将来可能"预留的空阶段；文档套件比正文还长。
