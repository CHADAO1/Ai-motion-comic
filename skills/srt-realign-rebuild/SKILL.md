# 字幕对齐重建 — 总控

把 B 语言字幕**整轨重建**到 A 语言字幕（基准轨）的时间轴上，做到**一条对一条、时间轴逐字节一致**。

**本文件只做调度**：执行到某阶段才读取对应文件。

## 0. 全局铁律

1. **先判定能否平移，再决定做法。** 取出两轨每条字幕的「起始时间」，算交集比例。
   - 交集 > 95% 且条数相同 → 只需替换文本，时间轴动都不用动。
   - 交集低（实测量级：1581 条中文 vs 1760 条英文，**仅 50 条起止时间重合**）→ **两轨是各自独立生成的，不存在平移关系**。此时禁止"对齐修补"，必须**废弃目标轨时间轴，逐条重写**。
2. **基准轨是唯一权威。** 基准轨有几条，交付就有几条；基准轨时间轴是什么，交付就是什么。**一条不多、一条不少、一个时间点不改**。
3. **文本必须用「行号 → 译文」的显式字典承载。** 禁止用文件名的自然排序、parts 分块顺序、行数累加来隐式表达行号——实测会整块错位（丢失一块 + 重复一块，全文偏移 150 行）。落盘格式：`zh_map.json`，键＝基准轨 1-based 条号。
4. **合轨后逐条比对时间轴，必须给出数值证据。** 结论不能是"时间轴一致了"，必须是"**不一致条数 = 0 / 1760**"，并附条数、序号连续性、单调性三个数。
5. **译文语义权威顺序**：原剧本/台本 > 基准轨文本（若基准轨是原文语言）> 人工判断。**专有名词全片必须单一译名**。
6. **交付前必查英文残留与专有名词错写。** 允许保留的术语（如 `Alpha`/`DNA`/`IP`/`Luna`）必须显式列白名单，其余残留一律清零。

## 1. 流程

| 阶段 | 动作 | 产出 / 读什么 |
|---|---|---|
| **S0 探基线** | 解析两轨 SRT（序号/时间轴/文本），统计条数与起始时间交集 | 判定走「平移」还是「重建」 |
| **S1 建译名表** | 通读基准轨 + 原剧本，建立 `00_标准译名对照表.md`（每个专有名词：标准译名 + 错误写法清单） | 译名基准 |
| **S2 出译文** | **按基准轨条号逐块产出译文**，写进 `zh_map.json`（键＝条号）；分批写，每批写完即校验键连续性 | `zh_map.json` |
| **S3 合轨** | 读基准轨时间轴 + 字典译文 → 重排序号为 1..N → 输出交付稿 | `scripts/rebuild_srt.py` |
| **S4 四道校验** | ①条数相等 ②时间轴逐条一致=0 处不符 ③序号连续 ④起始时间单调递增；再扫英文残留 + 专有名词黑名单 | 数值报告 |
| **S5 锚点抽查** | 取每块首末条 + 关键剧情点，人工核对「英文原文 ↔ 中文译文」是否真的对应（防整块错位） | `scripts/rebuild_srt.py --anchor` |
| **S6 交付** | 写入目标目录（编码/行尾跟基准轨或同目录同族文件一致），校验 MD5 | `md5sum` 双端一致 |

## 2. 合轨与体检脚本

`scripts/rebuild_srt.py`：

```bash
# 合轨：base.srt 的时间轴 + zh_map.json 的译文 → out.srt
python rebuild_srt.py build --base en.srt --map zh_map.json --out 中文字幕.srt \
    --newline crlf --bom none

# 体检：校验已有稿件是否与基准轨逐条对齐
python rebuild_srt.py check --base en.srt --target 中文字幕.srt

# 锚点抽查：按你给的行号打印「基准原文 ↔ 目标译文」
python rebuild_srt.py anchor --base en.srt --target 中文字幕.srt --lines 1,150,151,1760
```

**译文落盘约定**（`zh_map.json`）：

```json
{ "1": "我把我所会的一切都教给你了", "2": "现在你已经是独当一面的女巫了" }
```

键必须是**字符串化的一基条号**。缺键/多键由脚本直接报错终止，不做静默补位。

## 3. MODE 3 — 去标点拆条

**触发**：「字幕里不能出现标点符号」「标点的要断成两个字幕」「要无标点字幕」。

**前提**：基准轨与目标轨已逐条 1:1 对齐（若未对齐，先走 MODE 1）。**拆条会改变目标轨条数，因此与"条数必须等于基准轨"这条铁律天然冲突——动手前必须先向用户确认时间口径**，不要自行决定。

```bash
python scripts/strip_punct_split.py --base en.srt --target 中文字幕.srt \
    --out 中文字幕_无标点.srt --newline crlf --bom none
```

### 三条拆条铁律

1. **父窗口边界零漂移。** 拆出的首条起点 = 基准条起点，末条终点 = 基准条终点；中间按字数比例分配（带最低时长水位填充）。这样条数虽然变多，但**每个基准时间点仍与目标轨对齐**，是目前「去标点」与「时间轴一致」唯一能同时成立的口径。
   - 备用口径（用户可能有别的偏好，先问）：① 只删标点不拆条（条数不变）② 中英两轨一起拆（条数仍相等，但两种语言断点不齐）。
2. **只删不拆的字符要单独列。** 间隔号 `·`（如「芬里斯·康尼克」）按 · 拆会把姓名劈成两张卡 → 只删除、不拆分。书名号 `《》`（曲名/作品名）默认**保留**，属专用标记而非句读标点；是否保留要问用户。
3. **防闪卡兜底。** 若父窗口低于「段数 × `--min-seg-ms`（默认 300ms）」，就不拆，标点直接去掉、保留单卡——否则会产出 250ms 级别的卡片，肉眼根本看不见。**退回单卡的条目必须在报告里逐条列出**，让用户决定是否强行拆。

### 验收口径

| 项 | 期望 |
|---|---|
| 残留标点（除用户指定保留的） | **0**，并打印实际残留字符集 |
| 父窗口边界漂移 | **0** |
| 序号 | 连续 1..N |
| 时间轴 | 不重叠、起点严格递增 |
| 空文本 / 重复 | 0 |

## 4. 环境踩坑（实战记录）

- **网络盘（UNC）写入需要提权**：普通沙箱对 `\\192.168.x.x\...` 写入会 `Permission denied`；需以提权方式执行复制。
- **网络盘删文件会失败**：安全删除机制走本地回收站，对 UNC 路径报 `系统找不到指定的文件`；改用 Win32 `DeleteFileW`（Python `ctypes.windll.kernel32.DeleteFileW`）。
- **行尾/编码先采样再定**：读前 200 字节看是否有 UTF-8 BOM（`EF BB BF`）、是否 CRLF。用 Python 文本模式读会把 `\r\n` 归一成 `\n`，**校验行尾必须用 `'rb'` 读**。
- **同目录可能有"另一版"基准轨**：交付前 grep 一下同目录/子目录里是否有别的同名/近似字幕文件（实测发现 `his\` 下有另一份英文字幕，1759 条，与指定基准差异 1711/1759 条）。**以用户点名的文件为准，但必须把发现告知用户。**
- **需求会互相打架，先摆冲突再动手**：用户可能先要「时间轴与英文完全一致（条数 1:1）」，紧接着要「带标点的断成两条」——两者数学上不可能同时成立。**必须先把冲突讲清楚再让用户选口径**，不要默默按一种做。实测用户选了「拆条但保留英文边界」。
- **间隔号 `·` 容易被漏**：`BAD_RE` 扫描是最可靠的兜底——用白名单（`\w` + 中文 + 指定保留符号）反查残留，比枚举黑名单可靠。实测 2119 条里只揪出 1 处 `·`（「我，芬里斯·康尼克」）。
- **拆分结果要抽检"读起来是否自然"**：不能只看校验通过。要打印「原句 → 拆后各条 + 各条时长」，人眼扫一遍（实测发现 250ms 闪卡问题就是这么发现的）。
- **同一部剧会有多个版本共存，交付时必须带区分后缀**：实拍项目里同一目录可能先后要「无标点版」和「保留标点版」，而两份都叫《剧名中文字幕.srt》就会互相覆盖（用户就踩过这个：先要无标点，回头又要保留标点版）。**铁律：主文件名只给一份，其余版本加限定后缀**（如 `剧名中文字幕（带标点）.srt`），并明确告知用户两版差异，绝不静默覆盖。
- **历史备份要用脚本复核，不能只看"文件在"**：用户回要旧版本时，不要直接把备份扔出去。正确做法 = 用 `build`（配原始 `zh_map.json`）重新生成一份，与备份做 **MD5 比对**。实测两者 MD5 完全一致，既证明备份没损坏、也证明它确实等于 `en.srt + zh_map.json` 的确定性产物，可随时重现。
- **保留标点版 = `build` 的原生产物；无标点版 = `strip_punct_split.py` 的产物**：两者同源同基准轨，只有「是否去标点拆条」一步之差。别把两个脚本的用途搞混。
